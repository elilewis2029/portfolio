# Editor usability audit — 2026-10-08

Eli reported that "the save features are wonky still". This audit ran the owner-mode editor, the "+" sheet and the toolbar against the live Supabase project (`crggczdexbxziheacayz`) from a local production build (`next start`), signed in as the owner with Playwright, on a desktop viewport (1280×900) and a phone viewport (390×844, touch). All destructive tests used throwaway drafts named "AUDIT TEST …", deleted at the end. None of Eli's projects were edited, published, unpublished or deleted.

Severity: **blocks a save** = an edit is lost or not saved when the user thinks it is · **confusing** = the save works but the page misleads · **cosmetic**.

## Findings

### 1. Stale "Restored unsaved changes" after a successful Save — blocks a save · Fixed
**Steps.** Open a draft with `?edit=1`. Type `Calipers, Haas VF-2` into Tools (or leave a trailing space in any field, or type a slug with capitals). Save.
**Seen.** The page shows "Saved." and, right under it, the yellow "Restored unsaved changes … The saved version has changed since" box (screenshot `audit/before-saved-and-restored.png`). The fields show what was typed, not what was stored (`calipers, haas-vf-2`). The box comes back on every reload and on every later visit from the same browser. The browser also asks "Leave site?" when you go. If you press Save again, the old typed copy overwrites newer server values.
**Cause.** The browser keeps a copy of what you typed until it matches the saved version exactly. The server tidies the input before saving: it trims spaces, lowercases and hyphenates tools/skills/audience, slugifies the URL, reformats links and drops a year that isn't 4 digits. So the copy never matches and is never dropped. Clean edits (no tidying) worked, which is why this looked random.
**Fix.** Save now marks the copy it sends as "submitted". The server redirects with a fresh `saved=<timestamp>`, and the editor drops a submitted copy once that arrives and shows the stored values. A failed or signed-out Save does not send `saved`, so the copy is still restored in those cases. Typing after pressing Save creates a new, unsubmitted copy, which is kept.

### 2. Two kinds of Save; the big one skips photos — blocks a save · Fixed
**Steps.** Change a photo's caption or kind, then press the big Save at the bottom.
**Seen.** "Saved." appears, but the caption is not saved. Only the small Save next to each photo saves that row, and it gives no confirmation at all (screenshot `audit/before-photo-rows-phone.png`). The unsaved caption then sits in the browser copy, which led to more "Restored unsaved changes" boxes after reloads (two at once in one test).
**Fix.** The photo kind and caption fields now belong to the main form (`form="project-form"`), so one Save saves the fields and every photo's kind and caption. The per-row Save buttons are gone. A line above the photos says what Save covers and that ↑ ↓, Make cover and Remove act straight away. The Save bar now stays on screen over the photo list too (it used to scroll away at the end of the text fields).
**Checked.** Typed a caption, then pressed ↓ and Make cover before saving: the typed caption stays in its row (it moves with the photo) and is saved by the next Save. Removing a photo with a typed caption does not leave a stale copy.

### 3. "Make cover" hides the previous cover photo — blocks a save · Fixed
**Steps.** On a project whose cover has kind `hero`, press Make cover on another photo. View the page as a visitor.
**Seen.** The old cover is gone from the page. In the test, 3 photos in the editor, 2 on the page.
**Cause.** The page shows the cover at the top, then process photos (untyped, process, cad, drawing, test, failure) and before/after. A photo of kind `hero` that is no longer the cover falls into none of these groups.
**Fix.** Make cover now changes any other `hero` photo in the project to `process`, and the page shows a non-cover `hero` photo with the process photos (covers anything typed that way by hand). No live project was affected: a scan of all projects found no hidden photos.

### 4. Slug already taken — blocks a save · Fixed
**Steps.** Change Slug to another project's slug (e.g. `portable-wii`) together with other edits. Save.
**Seen.** Red message `duplicate key value violates unique constraint "projects_slug_key"`. None of the other edits were saved.
**Fix.** The server checks the slug first. If it is taken, everything else is saved and the message says "The URL /work/portable-wii is already used by another project, so the URL was not changed. Everything else was saved." The Save bar says "Saved, with one problem".

### 5. "Saved." lingers — confusing · Fixed
**Seen.** `?saved=1` stayed in the URL, so "Saved." showed again after a reload and stayed on screen while new, unsaved edits were being typed. It sat at the top of a long page, out of sight on a phone when Save is pressed at the bottom.
**Fix.** The status now sits next to the Save button in the sticky bar: "Unsaved changes" while typing, "Saving…" while the request runs (the button is disabled to stop double taps), then "Saved ✓ 6:15 AM". `saved` and `error` are removed from the URL after they are shown, so a reload doesn't repeat them (screenshot `audit/after-one-save-phone.png`).

### 6. Sign-in after an expired session lands on the home page — confusing · Fixed
**Steps.** Open the editor, clear cookies (or wait for the session to expire), press ↓ (or Make cover, Remove, Publish, Feature, Delete).
**Seen.** `/login?next=/`. After sign-in, you're on the home page and have to find the project again. (The main Save already returned to the editor.)
**Fix.** `requireOwner()` without an explicit target now returns to the page the action came from (same-site `Referer`). The login page says "You were signed out, so that change was not saved yet …" when it is returning to an editor (screenshot `audit/after-expired-login-phone.png`). Retested: an expired Save → sign in → back in the editor with the typed text restored → Save works.

### 7. "+" sheet loses its contents when closed — blocks a save · Fixed
**Steps.** Tap "+", choose a photo, type a note, close the sheet (×, Esc, or tap outside), reopen.
**Seen.** Empty sheet: photos and note gone. Closing while "Uploading photos…" was showing: the draft was still created on the server, but the sheet never showed the result or refreshed the grid.
**Fix.** The form stays mounted while the sheet is closed. Reopening shows the same photos and note, and a send that finished while it was closed shows its "Saved for chat: … Open →" result.

### 8. Publishing a page with `[TODO]` placeholders — confusing · Fixed
**Seen.** Publish (toolbar and /review) published straight away, and the project page shows field text as written, so `[TODO: number]` would be visible to recruiters.
**Fix.** When the page has TODOs, Publish asks first: "This page still has 1 [TODO] placeholder(s), and visitors will see them as written. Publish anyway?"

### 9. Save bar covers the focused field on a phone — confusing · Fixed
**Seen.** On 390 px the browser scrolls a tapped field or button to the bottom edge of the screen, under the sticky Save bar (in the test, the ↓ button of a photo row could not be tapped). The "+" button does not overlap Save (the bar keeps 80 px clear on the right).
**Fix.** `scroll-padding-bottom: 6rem` on the editor page, so anything scrolled into view stops above the bar.

### 10. Phone header 408 px wide on a 390 px screen in owner mode — cosmetic · Fixed
**Seen.** The "Owner" chip is cut off and the page scrolls sideways a little (`audit/before-header-overflow-phone.png`).
**Fix.** The chip is hidden below the `sm` breakpoint; the footer already has "Review · Sign out".

### 11. "+" sheet with an expired sign-in — blocks a save · Open
**Steps.** Open the sheet, let the session expire, choose photos, press Send or Save for chat.
**Seen.** The page jumps to `/login?next=/add`. The photos and the note are gone, and nothing says why.
**Proposed fix.** `prepareUploads` and `submitIntake` (app/add/actions.ts) return `{ ok: false, error: "signed-out" }` instead of redirecting. The sheet then shows "You were signed out. Sign in in a new tab, then press Send again" with a link to `/login` in a new tab, and keeps its state. About 20 lines.

### 12. "Done editing" with unsaved edits on iPhone — confusing · Open
On desktop Chromium, leaving with unsaved edits triggers the browser's "Leave site?" prompt. iOS Safari ignores `beforeunload`, so on an iPhone "Done editing" leaves without a warning. The text is not lost: it is kept in the browser and restored next time the editor opens, with a Discard link. With the new "Unsaved changes" label next to Save this matters less.
**Proposed fix.** Make "Done editing" a small client link that checks for a stored copy for this project and asks "You have unsaved changes. Leave anyway? They'll be kept on this phone."

### 13. Phone keyboard over the Save bar — not testable here
Headless Chromium has no on-screen keyboard. On iOS Safari a `position: sticky; bottom: 0` bar sits behind the keyboard while a field has focus; it reappears when the keyboard closes. Worth a 30-second check on Eli's phone: tap a caption, type, close the keyboard, Save.

### 14. Series order and year accept any text — confusing · Partly fixed
`first` in Series order or `25` in Year is saved as empty without a message. After fix 1, the field visibly empties after Save, which at least shows it wasn't accepted, and both fields now bring up the number keypad on phones (`inputMode="numeric"`). Still open: a line saying why, e.g. "Year must be 4 digits".

### 15. Delete only on the project page — cosmetic · Open
/review has Publish/Unpublish and Feature but no Delete; deleting a draft means opening it first. Delete confirms ("Delete … and its N photo(s)? This can't be undone.") and returns to /review. This works as described in DECISIONS item 4, so it is listed only for completeness.

### 16. "+" note matched to an existing project — confusing · Open (by design)
The note "AUDIT TEST sheet throwaway: a purple test block…" was appended to the existing draft "AUDIT TEST throwaway" rather than creating a new one. The result line says so clearly ("Added 1 photo(s) to AUDIT TEST throwaway. Open →"), so this is the intended "append when the note names a project" behaviour, but a near-match can surprise. No change proposed unless it happens with real projects.

## After deploying

Browsers that used the old editor may still hold stale copies from bug 1. The first time Eli opens an affected project, the yellow "Restored unsaved changes" box may appear once; press **Discard** if the text in it is old. Old per-photo copies are no longer read and do nothing.

## What was tested and how

- Owner session minted with the service key (`generateLink` → `verifyOtp`), loaded into Playwright; phone context 390×844, touch, DPR 2.
- Throwaway drafts: `npm run portfolio -- new` with 3 generated photos, plus 2 drafts created through the "+" sheet; all deleted with `npm run portfolio -- delete`.
- Each fix was retested on desktop and phone after `npm run lint` and a production build: save with tidied input, reload, photo caption + ↓ + Make cover + Save, slug clash, slug rename, public page photo count, expired Save and expired ↓, Publish with a TODO, "+" sheet close/reopen and close mid-send.
